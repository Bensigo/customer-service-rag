# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

customer-service-rag — a Retrieval-Augmented Generation (RAG) system for customer service. Python 3.12 managed with uv, FastAPI, src layout (package `app` in `src/app/`, tests in `tests/`). Roadmap lives in GitHub issue #1; the architecture overview is below and the decision log is in `docs/decisions.md`. User-facing docs are in `README.md`.

`main` is protected: changes land via pull request with green CI (ruff + pytest), never a direct push.

## Commands

- `uv sync` — install/refresh dependencies (pinned via `uv.lock`)
- `make test` — run the test suite (pytest)
- `uv run pytest tests/test_config.py::test_settings_defaults -v` — run a single test
- `make lint` — ruff lint + format check
- `make format` — auto-format and auto-fix lint
- `make run` — start the API locally (uvicorn with reload)
- `docker compose up --build` — run the full stack (app :8000, Qdrant :6333, Redis :6379); Ollama is expected on the host at :11434, not in compose
- `make compose-check` — validate compose.yaml

## Architecture overview

Two pipelines over a FastAPI app (`src/app/main.py` builds every long-lived resource once at startup, shares it via `app.state`, and closes it on shutdown). The module layout:

- `src/app/api/` — HTTP boundary: `documents.py` (upload/update; size cap, doc-id validation, ingest run off the event loop behind a single-permit limiter) and `chat.py` (the query pipeline as a handler; owns the one `request_summary` observability seam).
- `src/app/ingestion/` — `extractors.py` (txt/md/pdf via pypdf, no OCR), `chunker.py` (sentence-aware overlapping windows), `pipeline.py` (orchestration with compensation-based atomicity, superseded-version sweep, and cache invalidation).
- `src/app/retrieval/` — `embedder.py` (Ollama embeddings), `hybrid.py` (BM25 + vector with RRF fusion), `reranker.py` (LLM pointwise scoring via Ollama), `pool.py` (per-slot read connections for concurrent chat reads).
- `src/app/stores/` — `chunk_store.py` (versioned SQLite), `bm25_index.py` (SQLite FTS5), `vector_store.py` (Qdrant), `cache.py` (Redis response cache + tag-set invalidation), `sessions.py` (Redis conversation history).
- `src/app/chat/` — `fingerprint.py` (first-turn cache key), `context.py` (context assembly + prompt-injection guards), `llm.py` (the `LLMClient` Protocol and its LangChain Ollama/Anthropic adapters).
- `src/app/eval/` — retrieval eval harness and its `python -m app.eval` CLI.

**Ingestion pipeline.** A document upload is extracted to text, chunked, and embedded (Ollama) *before* any write, so the likeliest failure aborts with nothing to undo. The new version is written to the versioned SQLite chunk store, the FTS5 BM25 index, and the Qdrant vector store; any write failure is compensated by deleting just the new version, leaving the previously active one serving. Superseded versions are swept only after the new one is fully written (the sweep also heals a prior failed cleanup), and finally the response cache is invalidated for that doc id.

**Query pipeline.** A chat request is fingerprinted on its normalized first-turn message; a cache hit skips retrieval and the LLM entirely. On a miss, BM25 and vector search run and are fused with Reciprocal Rank Fusion, an LLM reranker (Ollama pointwise scoring) reorders the top candidates, context is assembled from the chosen chunks plus conversation history, and the answer is generated by Ollama `gemma4` (or Claude, if `LLM_PROVIDER=anthropic`). The model is never called — a fixed escalation answer is returned instead — when retrieval is empty *or* the reranker's best relevance score falls below `min_rerank_score` (weak, not-relevant-enough retrieval); a total reranker outage leaves no relevance signal and never forces a refusal (it answers from the fused order). A successful answer is written back to the cache, tagged by its source doc ids for later invalidation.

Design rationale for every choice is in `docs/decisions.md`.

## Development Workflow

Every change, no matter how small, follows this workflow in order. These rules are non-negotiable.

### 1. Plan first — track everything on GitHub

- Before writing any code, produce a short written plan and file it as a GitHub issue (`gh issue create`).
- Break large features into multiple small issues; each issue must be deliverable as one small PR.
- Link every PR to its issue (`Closes #<n>`).

### 2. Test-driven development (red-green-refactor)

All code is written test-first:

1. **Red** — write a failing test that describes the desired behavior. Run it and confirm it fails for the expected reason before writing any implementation.
2. **Green** — write the minimum implementation that makes the test pass. Run the tests and confirm they pass.
3. **Refactor** — clean up the code while keeping all tests green.

Never write implementation code before a failing test exists, and never weaken or delete a test to get to green.

### 3. Subagent code review — before every PR

- After implementation is complete and tests pass, dispatch a code-review subagent (e.g. the `code-review` skill or a code-reviewer agent) to review the full diff.
- Fix all confirmed findings before opening the PR; note any disputed findings in the PR description.

### 4. Security check — before every PR

- Run a security review of the diff (e.g. `/security-review`) in addition to the code review, and fix what it finds.
- RAG-specific rules:
  - Treat retrieved documents and user messages as untrusted input — guard against prompt injection reaching system prompts or tool calls.
  - Never log or index customer PII without scrubbing it first.
  - All secrets (LLM API keys, database URLs) live in `.env` (gitignored) and are read from environment variables — never hardcoded.

### 5. Small PRs only

- Never commit directly to `main`. Create one branch per issue (`feat/<issue>-<slug>`, `fix/<issue>-<slug>`).
- Keep each PR small and focused — one issue, one concern, ideally under ~400 changed lines. If it grows beyond that, split it.
- A PR is ready only when it has: passing tests written via TDD, a completed subagent code review, a security check, and a linked issue.

### 6. Code standards

- Prefer simple, readable code over clever code; small functions with clear names.
- Handle errors explicitly — no silently swallowed exceptions.
- No dead code, commented-out code, or TODOs without a linked issue.
- Vet and pin new dependencies before adding them.
